# TRANSAQ: справочники (RQ_STARTUP) и инструменты (R_SEC_NEW)

Дата: 3 ноября 2026. Источник: `txmlconnector64-6.47.2.26.4.dll`, демо-сервер Finam. Обозначения статусов те же, что в [connect.md](connect.md): **S** — сверено с XML-колбэками DLL на демо-сервере, **D** — прочитано в декомпиляторе, **I** — вывод.

Реализация: [`native/xmlcompat`](../../native/xmlcompat). XML строится в структуры [`client/commands`](../../client/commands/main.go), которые уже используют клиенты.

## Методика

DLL под Wine подключалась к демо-серверу через логирующий прокси, harness сохранял все колбэки целиком. Каждая запись разобрана по декомпилированному обработчику и сверена с колбэком DLL из той же сессии. Справочники проверены побайтно, инструменты — по значениям полей.

## RQ_STARTUP

Ответ — шесть секций подряд в порядке вызовов из `FUN_180357e00`. Каждая секция завершается маркером `-1`. Разбор поглощает ответ демо-сервера (4355 байт) ровно до конца — **S**.

| Секция | Функция | Запись | Конец |
|---|---|---|---|
| рынки | `FUN_1803953e0` | `B:id Z10:код Z24:имя B B B B` | `B:0xff W` |
| типы режимов | `FUN_180395820` | `B:id Z32:имя Z8 B` | `B:0xff` |
| режимы (boards) | `FUN_180395b40` | `W:номер B:рынок Z7:код Z30:имя W B Z8 B B:тип` | `W:0xffff` |
| типы бумаг | `FUN_180395f70` | `B:id Z10 Z24 B B B` | `B:0xff` |
| виды свечей | `FUN_1803b88b0` | `B:id Z12:имя L:период L` | `B:0xff` |
| колонки | `FUN_1803b7ee0` | `B:id B Z32:заголовок Z16:код` | `B:0xff` |

Строки — CP1251. Правила формирования XML (совпадение с DLL **побайтно**, **S**):

- `<markets>`: `id` и **код** рынка (`ММВБ`, `FORTS`), отсортированные по `id`.
- `<boards>`: порядок как в ответе. Рынок 5 (опционы FORTS) DLL выводит как 4 — **D** (`FUN_1800c07f0`), **S**.
- `<candlekinds>`: порядок как в ответе.

## Записи RQ_MAIN

Ответ RQ_MAIN — поток записей `B:тег …`. Диспетчер — `FUN_18038d7d0`, в `switch` значение равно `тег−1`.

- У 12 тегов после тега идёт размер `W` (BE): 0x02 R_CLN_NEW, 0x03 R_ORD_NEW, 0x04 R_TRD, 0x08 R_ALLTRADE, 0x10 R_ORD_MODIFY, 0x28 R_SEC_NEW, 0x3a R_ORD_RENEW, 0x3b R_CLIENT_ASSET, 0x34 R_BOARD, 0x54 R_STOP, 0x5e R_SEC_PARAM, 0x5f R_WRAPPER,
  0x66 R_DOUBLELEG, 0x7c ReadICA. Перед каждым следующим тегом DLL переходит на конец записи, поэтому такие записи можно пропускать — **D**.
- Обёртка R_WRAPPER (0x5f) задаёт границу, а внутри идут обычные записи.
- Остальные ~70 тегов размера не имеют, и для разбора потока нужен формат каждого. Реализован R_DATE (0x3d, `L` — секунды на 00:00 дня торгов) — **S**.
- Снапшот демо-сервера: R_DATE, 17 176 × R_SEC_NEW, 17 176 × R_SEC_PARAM, 5 × R_DOUBLELEG. Затем идёт 0x62 с данными счёта (формат не разобран).
- Форматы остальных записей (0x34, 0x38, 0x39, 0x42, 0x43, 0x4f, 0x5c, 0x5d, 0x66, 0x6b, 0x6e, 0x6f–0x79, 0x7c) и статистика тегов живых дампов — [records.md](records.md).

## R_SEC_NEW (0x28)

Обработчик — `FUN_180398640`. Все 17 176 записей демо-сервера разбираются без остатка до границы записи — **S**.

```
W:secid  B:рынок  B:вид  B:класс  Z25:seccode  Z30:shortname  Z12:ISIN
B  L  B:флаги (0x30 — call/put)  L
[вид 4|5: B:флаги производного; если &0x0c — Z25:базовый актив]
B:свойства
повторять до W:0xffff — параметры режима (pit):
    W:номер режима  L:лот  L:делитель лота  L:шаг (в 10^-decimals)  B:decimals  B
    D:point_cost (double LE)  Z12  B:режим по умолчанию  L  Z4:валюта расчётов
Z4:валюта
необязательно, пока не кончилась запись: B B | L + 16 байт пояса | Z5:MIC Z25:ticker | L L Z25 Z6 | B
```

`L:делитель лота` есть при версии протокола сервера > 0x42 (демо: 68) — **D**.

Отображение в `<security>` (совпадение со всеми 17 176 инструментами DLL, **S**):

| Поле XML | Источник |
|---|---|
| `secid`, `seccode`, `shortname` | одноимённые поля |
| `instrclass` | символ `класс`; при 0 — по виду бумаги: 0 E, 1 B, 4 F, 5 O, 7 I, 15 C, 16 S |
| `market` | рынок; 5 → 4 |
| `sectype` | по виду бумаги: 0 SHARE, 1 BOND, 4 FUT, 5 OPT, 7 IDX, 14 MCT, 15 ETS_CURRENCY, 16 ETS_SWAP |
| `board` | код режима, у которого стоит флаг «по умолчанию» (по номеру из RQ_STARTUP) |
| `decimals`, `lotdivider` | из режима по умолчанию |
| `lotsize` | лот режима по умолчанию; на FORTS (рынки 4, 5) всегда 1 |
| `minstep` | шаг × 10^-decimals; печатается с `decimals` знаками без хвостовых нулей, минимум одна цифра после точки (`0.01`, `1.0`) |
| `point_cost` | double, 6 значащих цифр (`%g`): `161.1146` → `161.115` |
| `currency` | валюта бумаги; пустая на рынке 1 → `RUR` |
| `currencyid` | валюта режима, иначе валюта бумаги; `RUR` → `RUB` |

## Производные поля (эталон 4 ноября 2026)

Генератор дампа `get_securities` — `FUN_18011f4a0` с порядком элементов, отличным от чанкового (см. ниже). Состояние считается в обработчике `FUN_180398640` и хранится в записи. Модель проверена побайтным совпадением со всеми 499 инструментами снапшот-фикстуры (`TestSecurityXMLBytes`) и **со всем живым снапшотом 4.11.2026: 35 чанков `<securities>` (17 199 инструментов) и дамп `get_securities` совпали с DLL побайтно** — **S**.

Порядок элементов в чанке загрузки (фикстура и живой захват одинаковы): `sec_tz, seccode, instrclass, currency, board, shortname, decimals, market, sectype, opmask, minstep, lotsize, lotdivider, point_cost, quotestype, MIC, ticker, currencyid`. Пустые `currency`, `MIC`, `ticker`, `currencyid` не печатаются; `minstep…point_cost` — только когда у бумаги есть режим; `opmask` — только когда `active="true"`.

| Поле | Правило | Статус |
|---|---|---|
| `F` — байт opmask | `Raw[1]` типа бумаг из RQ_STARTUP (`FUN_180395f70`, смещение записи `+0x4d`) \| (`свойства&2`→1) \| (`свойства&4`→2) | D+S |
| `active` | есть pit и `флаги&3==3` и вид≠IDX(7) и не (рынок 14 и `Tail2==7`, DCF) и не (вид 4/5 и `DerivFlags&4` без `&8`) | D+S |
| `opmask/ioc`, `cancelbalance` | `F&0x01` | D+S |
| `opmask/fok`, `immorcancel` | `F&0x02` | D+S |
| `opmask/bymarket` | `F&0x04` и `флаги&0x04` — бит ставится записью RQ_MAIN `R_SEC_MKT_PERMIT` (тег 0x0e) через `FUN_180264150` (случай 4: `б4&0xfb | (val?4:0)`); R_SEC_ONOFF (0x0d) правит `б4&0xfc|val` — отсюда `active` в живом потоке | D+S |
| `opmask/nosplit` | `F&0x08` | D+S |
| `opmask/usecredit` | `F&0x10` | D+S |
| `quotestype` | гейт: вид≠0x11 и `Byte2&2` режима по умолчанию из RQ_STARTUP; затем: рынок 14 (MCT) → `Tail1` записи; вид 7 → 0; рынок 12 → 2; иначе 1 (`FUN_1801dfaa0`, `FUN_1801e0080`, `FUN_1801dfbe0`) | D+S |
| `MIC`, `ticker` | хвостовые `Z5`, `Z25` записи (`FUN_18011f4a0`: длина>`+0xb9`>0) | S |

На живом снапшоте 4.11 `bymarket="yes"` у 3846 из 17 199 бумаг — состояние полностью из байта `флаги` записей (записей 0x0d/0x0e за 81 сессию не было). На фикстуре 3.11 — 22 из 97 акций TQBR; путь permit-мутации подтверждён декомпилятором и юнит-тестом, живого permit-наблюдения пока нет.

## `<pits>`

Генератор `FUN_18012fd10`; DLL выдаёт `<pits>` чанком на каждый RQ_MAIN опрос снапшота, парой к `<securities>` (35 пар в живом захвате 4 ноября, сверено **побайтно**). Внутри — каждый режим каждой новой бумаги: **режим по умолчанию первым**, затем остальные в порядке записи; атрибуты `<pit seccode="X" board ="Y">` (пробел перед `=` — да, у DLL так); элементы `market, [currencyid], decimals, minstep, lotsize, lotdivider, point_cost`. Правила из живого сравнения 35×N элементов: `market` — байт рынка режима (5→4); `lotsize` — на FORTS (рынок 4/5) всегда 1; `currencyid` — валюта режима, иначе валюта бумаги (на рынке 1 по умолчанию `RUR`), `RUR`→`RUB`, пустая — элемент отсутствует. Экраны XML — таблица эскейпа DLL (см. ниже).

## Экранирование XML

Таблица сущностей DLL (`.rdata` 0x180829378): `& < > ' "` → `&amp; &gt; &lt; &apos; &quot;`. Апостроф — как `&apos;`, не `&#39;` (на этом различии поймали расхождение в 46 инструментах с `&#39;` в `shortname` при сверке живого дампа). CDATA у `sec_tz` не экранируется. Ошибка DLL: `</ticker>` пишется как `<ticker>` (`FUN_18011f4a0`) — не воспроизводим, при побайтовом сравнении ждать расхождение только там; на демо тикеров нет.

## Порядок дампа `get_securities`

Отличается от порядка чанков загрузки: бумаги сгруппированы по байту `market` записи (возрастание: 1, 4, 14), внутри группы отсортированы по `seccode` (порядок сравнения строк C). Дамп пишется другим генератором и другим порядком элементов: `sec_tz, board, seccode, instrclass, currency, shortname, decimals, market, minstep…, point_cost, opmask, [MIC], [ticker], sectype, quotestype, [currencyid]`. Проверено **побайтным** совпадением дампа реплея с живым дампом DLL (17 199 инструментов, 4 ноября) — **S**.

## R_SEC_PARAM (0x5e) — маска параметров и `<sec_info_upd>`

Размерная запись; в снапшоте идёт строго после каждой R_SEC_NEW. Тело: `W:secid`, `L:маска (Int64 packed)`, далее значения по установленным битам маски, каждое читается только если в буфере ещё есть данные (`FUN_1801be120`). В живом снапшоте 4.11 (17 199 бумаг + обновления) встречены маски `0x1cc0, 0x3cc0, 0x3880, 0x38cf, 0x3c80, 0x1c80, 0x1880, 0x1f80, 0x3cfb, 0x3ccf` и `0x100` (3719 записи — пост-снапшотные обновления); биты: `0x1/0x2/0x4` — блоки по 5 int в +0x204/+0x218/+0x22c (только FUT/OPT, `FUN_180264840`), `0x8` — режим+double (`180264bb0`), `0x10/0x20` — int в +0x1f0/+0x1f4 (`180264c70`), `0x40` — min/max price (`180264d50`: int в +0xb6, деление на 1000 с округлением к целому — `1801dd2a0`), `0x80` — word в +0x28e, `0x100/0x200` — double (`1802649e0/180264aa0`), `0x400` — байты zalog/oblig в +0x19a/+0x19b (`180264150` cases 1/2), `0x800` — бит 0x08 флага +0xb4, `0x1000` — бит 0x01 байта +0xb5, `0x2000` — int в +0x168 (`180264010`). Событие в очередь `1801e9760(запись+0x3c8, режим)`.

XML-событие `FUN_180107800` (`<sec_info_upd>`): `secid, seccode, market`, далее по битам маски события: `bit0` — `buy_deposit` (вид 4) либо `bgo_c` (вид 5); `bit1` — `sell_deposit`/`bgo_nc`; `bit2` — `bgo_buy` (только вид 5, иначе исключение "Wrong sectype"); `bit3` — `point_cost` (double, 6 значащих); `bit4/5` — `minprice`/`maxprice` (формат по decimals). Денежные значения int — `/100` с двумя знаками (`FUN_180053620(_,int,2,_)`). Живая сверка 4.11: 684 события — 44 штуки формы `buy,sell,point_cost,min,max` (FUT) и 640 формы `bgo_c,bgo_nc,bgo_buy,point_cost` (OPT); порядок полей и формат совпали с разбором — **S для формы**, соответствие «бит сети → бит события» и распаковка значений из тела — **D**.

**Реализация в Go (2026-11-04, задача 8):** `native/records/secparam.go` + `native/events_secparam.go` + `xmlcompat.SecInfoUpdateXML`; события доставляются и в загрузке (`ClientConfig.OnLoadEvent`), и в `Run` (`Connector`). Фикстура окна `native/records/testdata/secparam-live.hex.gz` (600 записей) + `sec_info_upd-dll.xml.gz` (200 колбэков) — рендер **побайтно 200/200**, полная независимая сверка по локальному E07-захвату — 684/684 (включая 42 FUT с decimals 1–4). Ограничение §8.12: в окне фикстуры identity (`seccode`/`market`/`point_cost`) сеются из ожидаемых XML-строк и `Kind`/`Pits` не засеяны (полная независимость потребует R_SEC_NEW-фикстуры окна); это отмечено в комментарии теста.

**S (живой захват E07, 2026-11-04, демо):** в загрузке пришло 18 284 записи 0x5e; маски:
`0x3cc0` — 9998, `0x1cc0` — 5437, `0x100` — 1085, `0x3ccf` — 638, `0x3880` — 605, `0x1f80` — 196,
`0x3c80` — 130, `0x1880` — 118, `0x3cfb` — 44, `0x1c80` — 31, `0x38cf` — 2. DLL отдала 684 колбэка
`<sec_info_upd>`: ровно записи с установленным битом маски **0x8** (638+2 — форма OPT
`bgo_c/bgo_nc/bgo_buy/point_cost`; 44 — форма FUT `buy_deposit/sell_deposit/point_cost/minprice/maxprice`),
порядок `secid` совпал 1:1 (684/684); записи без бита 0x8 колбэков не дают. Фикстуры для задачи 8:

Смежные теги снапшота: R_SEC_RATE (0x0a) — `W:secid L:значение` в +0xb8 (974 записи в захвате 4.11, колбэков не генерирует); `R_SEC_ZALOG/OBLIG/ONOFF/MKT_PERMIT` (0x0b–0x0e) — `W secid B val` в `FUN_180264150` (0x0d→`б4&0xfc|val`, 0x0e→бит 0x04 +0xb4). ## RQ_SEC_SPEC (15): запрос, ответ и spec-поля — S/D

DLL отправляет RQ_SEC_SPEC автоматически после подписки (`RQ_SUBSCRIBE`): запрос — простой список
`W secid` **без счётчика и терминатора**; при подписке на несколько бумаг одной командой — один
кадр со списком в обратном порядке XML-элементов (**S**, r12: подписка `<secid>26</secid>
`<secid>379</secid><secid>20583</secid>` → `RQ_SUBSCRIBE` 3 элемента, `RQ_SEC_SPEC` payload
`5067017b001a`). Ответ — кадр, состоящий из подряд идущих записей `W secid; G mask;` и значений по
битам маски в порядке возрастания бита (парсер — `FUN_1803bac90`, конец — 0xffff или конец
буфера; после разбора `symbol+0xec = 1`). Типы/поля маски (D, полная таблица и живые значения —
`native/testdata/secinfo-live.md`): 0 Z75 secname, 1 Z9 pname, 2 Z4 валюта, 3 G facevalue,
5 L clearing_price (FUT), 8 L mat_date (дни Unix), 9 L coupon_value (/100), 10 L coupon_period,
11 L coupon_date (дни), 19 L minprice (FUT), 20 L maxprice (FUT), 24/25 G buy/sell_deposit (/100),
32 Z3 currencyid, 36 Z12 isin, 40 Z160 url; прочие биты (4,6,7,12–17,21–23,26,27,30,31,33–35,
37–39,41) — значения встречались, смысл не установлен (**I**).

`get_securities_info` (`FUN_180197e60` → `FUN_1800f02f0` → рендер `FUN_180105990`) **не ходит в
сервер**: отдаёт `<sec_info>` из каталога и этого spec-кэша (**S**); если кэша нет — исключение
`GetSecSpec returned null` (I). Живые фикстуры: `native/testdata/secinfo-live.hex.gz` (281 байт —
три ответа RQ_SEC_SPEC подряд), `secinfo-dll.xml.gz` (5 колбэков `<sec_info>`), `secspec-request.hex`
(`5067017b001a`); разбор полей — `native/testdata/secinfo-live.md`.

## Что не разобрано

- R_DOUBLELEG, тег 0x62 и другие теги без размера.
- `<client>`, `<positions>`, `<overnight>` — торговый контур (M6). DLL отдаёт их в конце загрузки перед `connected="true"` (в живом захвате 4.11 видно); нативный коннектор пока не эмитит.

## Воспроизведение

```sh
go test ./native/xmlcompat        # включает TestSecurityXMLBytes — побайтовая сверка <security> с фикстурой DLL
# полная сверка на локальном захвате (вне репозитория):
TXML_DEMO_MAIN=main.hex TXML_DEMO_XML=dll.xml go test -run SecuritiesFull -v ./native/records
```

Фикстуры в `native/records/testdata` — справочные данные демо-сервера без полей счёта: ответ RQ_STARTUP, первый ответ RQ_MAIN (499 инструментов) и соответствующие колбэки DLL.

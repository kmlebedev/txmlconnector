# TRANSAQ: подключение, логин и начальная загрузка (встроенный криптопрофиль)

Дата: 3 ноября 2026. Источник: `txmlconnector64-6.47.2.26.4.dll`, SHA-256 `a197e2625e53c0df453687ae1b20ef2ae1a05e034cd20c424a7014b0c9726342`. Адреса ниже — VA при базе `0x180000000`.

Реализация на Go: [`native/cryptoprofile`](../../native/cryptoprofile), [`native/wire`](../../native/wire), [`native/session`](../../native/session); CLI [`tools/native-login`](../../tools/native-login), расшифровщик захватов [`tools/wire-decode`](../../tools/wire-decode).

Статусы: **S** — подтверждено на демо-сервере Finam (`tr1-demo5.finam.ru:3939`, 3 ноября 2026), **R** — подтверждено runtime (DLL под Wine 11.21 + Rosetta против локального стаба), **D** — прочитано в декомпиляторе Ghidra 12.2, **I** — вывод/гипотеза.

## Методика

1. DLL запускалась через [`tools/reference-harness`](../../tools/reference-harness) с `<command id="connect">` на `127.0.0.1` и тестовыми логином/паролем.
2. При `TC_DLL_LOG_LEVEL=3` журнал `*_ts.log` печатает логическое содержимое запросов (`RQ: 1`, `WR: C:x;W:78;...`). Это дало открытый текст для сопоставления с шифртекстом.
3. Ghidra headless: функции найдены по ссылкам на строки журнала (`RQ_LOGIN return incorrect buffer`, `incorrect server response`).
4. Python-стаб отвечал по восстановленному формату; DLL принимала ответы и продвигалась по сценарию. Это проверка обеих сторон обмена.
5. Демо-доступ Finam: DLL и Go-клиент подключались через логирующий TCP-прокси; захваты расшифрованы `tools/wire-decode` с проверкой CRC каждого кадра. Сырые захваты содержат данные счёта и в репозиторий не входят.

## Кадр

Открытый заголовок, 8 байт (`FUN_1801bfb20` отправка, `FUN_1801bfef0` приём) — **D**, **R**:

| Байт | Поле |
|---|---|
| 0 | флаги: `&3` = 1 запрос, 2 ответ, 3 BYE; `0x80` — payload без шифрования |
| 1 | тип запроса; в ответе должен совпадать с запросом (`FUN_180355d50`) |
| 2–3 | длина payload, BE, не больше `0xfff0` |
| 4–5 | CRC-16/CCITT-FALSE открытого payload, BE |
| 6–7 | CRC-16/CCITT-FALSE байтов 0–5, BE |

Заголовок и payload шифруются **раздельно**, каждый раз с начала гаммы (тот же ключ и синхропосылка). Пустой payload: длина 0, CRC `0xffff`.

## Криптография

ГОСТ 28147-89, 32 раунда, стандартный порядок ключей; ключи и слова блока — little-endian (`FUN_1801bc170`, `FUN_180439d90`) — **D**, **R**.

- S-блоки: набор 3 (`FUN_180439c70(ctx, 3)`), четыре **8-битные** таблицы по 256 байт с VA `0x1809bea50`. Это не стандартные 4-битные узлы ГОСТ; таблица встроена в `native/cryptoprofile/tables.go`.
- C→S: гаммирование (`FUN_18043a520`): шифруется синхропосылка, затем на каждый блок `N2 += 0x01010104 (mod 2^32−1)`, `N1 += 0x01010101`.
- S→C: CFB (`FUN_18043a5d0` шифрование, `FUN_18043a660` расшифровка).
- Ключ по умолчанию — 32 байта с VA `0x180856010`, синхропосылка — 8 байт с `0x180856058`.
- Ключ пароля: `SHA-1(password)`, дополненный до 32 байт: `out[i] = rotl8(out[i-20] − i + 32, 3) ^ 0x97` (`FUN_1801bc080` → `FUN_18043d370`).

## Типы полей

| Трасса DLL | Запись / чтение | Кодирование |
|---|---|---|
| `C`, `B` | `FUN_1801be680`, `FUN_1801bd290` | 1 байт |
| `W` | `FUN_1801be710`, `FUN_1801bd5d0` | u16 BE |
| `Zn` | `FUN_1801be3e0`, `FUN_1801bd170` | до n байт + NUL |
| `Bn` | `FUN_1801be5d0`, `FUN_1801bd420` | n байт без длины |
| `L`, `G` | `FUN_1801be7d0`/`FUN_1801be970`, `FUN_1801bd7b0` | упакованное целое |

Упакованное целое: первый байт — `(|v| & 0xf) << 4 | sign << 3 | k`, затем k байт `|v| >> 4` little-endian. Пример из трассы: `L:16782022` → `63 2c 01 10`.

## RQ_LOGIN

Запрос, **R**: `C:'x' W:78 W:1 W:540 Z12:login W:65512`. 78 — версия протокола (`PRO# …/78` в журнале). 540 (`0x21c`) используется, пока `DAT_1809dd9c0 == 0`. 65512 — размер буфера минус заголовок. Пароль в RQ_LOGIN не передаётся.

Ответ, **D** + **R**: `B:flags`, `B:n`, `Bn:challenge`; если `flags & 1` — блок версии `Z32`, `L`, `L`. Флаги `4`/`8` DLL превращает в коды 0xc/0xd без challenge. Их смысл неизвестен; DLL всё равно шлёт RQ_PWD со случайными байтами, Go-клиент сразу возвращает ошибку.

## RQ_PWD

Запрос, **R**:

```
B<n>: challenge, зашифрованный гаммой ГОСТ на ключе пароля и синхропосылке по умолчанию
Z16: имя компьютера   Z32: имя пользователя   Z80: строка ОС
G: 64-битный идентификатор (I: из данных сетевого адаптера)
L…: до 4 ненулевых 32-битных значений (I: адреса адаптеров), затем L:0
B: DAT_1809d4064 (наблюдалось 0)
```

Пример: challenge `0102030405060708` + пароль `TESTPASS` → `211cf3ef536a73bf`.

Ответ, **D** + **R**: `B:status`. При `0x0e` далее идёт `Z0x103` — текст ошибки, при прочих ненулевых — только код. При 0 идут 32 байта ключа и 8 байт синхропосылки, каждые расшифровываются CFB (ключ пароля, синхропосылка по умолчанию) отдельно. Дальше обязательные `B B B L B B B B L` (4-е — таймаут сессии от сервера) и необязательные поля; полный порядок — в `parsePwdReply`. Подтверждены runtime: `UID` (L) и `SID` (B) — журнал показал `SID# 7 UID# 4242` для значений стаба. На демо-сервере разбор Go совпал с журналом DLL: `SYS# 626`, `BLD# 4`, `PRO# 68`, `UID#` (значение аккаунта маскировано), `SID# 0` — **S**.

Демо-сервер принял RQ_PWD Go-клиента со строками хоста macOS (`darwin/arm64`) и без адресов — **S**.

## Переподключение и восстановление: RQ_RELOGIN (63) и RQ_RECOVER (64)

Восстановление потерянного соединения выполняет общий отправитель запросов `FUN_180355d50`.
Адреса ниже — VA при базе `0x180000000` (DLL 6.47.2.26.4). Статусы: **D** — прочитано в
декомпиляторе Ghidra 12.2, **I** — вывод; **S** — подтверждено живым захватом DLL на
демо-сервере (RE-2, эксперимент E05, 2026-11-04; см. «Подтверждение живым захватом» ниже и
`native/session/testdata/recover-{short,long}-live.*`). Места, которые нельзя закрыть без живого
прогона, помечены «не проверено на захвате (RE-2)».

### Условия и порядок восстановления

1. Транспортная ошибка обычного запроса не возвращается вызывающему: `FUN_180355d50` входит в цикл
   восстановления. Исключения — типы `RQ_LOGIN` (1), `RQ_PWD` (0x2e), `RQ_LOGOUT` (2),
   `RQ_RELOGIN` (0x3f), `RQ_RECOVER` (0x40), `RQ_HANDSHAKE` (0x6a) и 0x7f: для них ошибка
   отдаётся сразу (`0x1803562b6`–`0x18035631b`, второй экземпляр `0x180356a93`; сами типы 63/64
   не инкрементируют счётчик запросов, `0x180355f28`, `0x180355f32`) — **D**.
2. Цикл: `ret = FUN_1803d27b0(conn, stream, remaining)`, пока `ret < 0` — `Sleep(1000)` и
   повтор (`0x180356320`–`0x1803565fb`; второй экземпляр `0x180356b05`–`0x180356dd8`).
   Первая попытка выполняется сразу; пауза между попытками фиксированная — 1 с, экспоненциального
   роста в DLL нет — **D**. (В плане ожидались паузы «1, 2, 4 … 30 с»; в этой сборке это не так —
   расхождение зафиксировано здесь, реализация должна повторять DLL.)
3. Окно восстановления — таймер, который инициализируется в `0x180355f0f`–`0x180355f1b`
   значением `param_5`; при `param_5 == -1` берётся `session_timeout` из объекта сессии
   (`conn+0x18`, поле `+0x1f8`) — **D**. Значение `session_timeout` приходит из ответа RQ_PWD;
   в `FUN_1803895c0` оно нормируется: `0` — берётся серверное, `< 0x14` — 20000 мс,
   `< 300` — значение×1000 (то есть в `connect` и в ответе сервера это секунды), дальше
   `request_timeout` нормируется так же, и если он ≥ `session_timeout`, становится
   `session_timeout/2` — **D**. Когда окно истекло между попытками, DLL бросает C++-исключение
   `"Request timeout."` (`FUN_18073a228` = `RaiseException(0xe06d7363)`; строки VA
   `0x18084ece0`, `0x18084ed10`; переход `0x18035720f`) — **D**. Других лимитов по числу
   попыток нет: ограничивает только время — **D**.
4. Последствия исключения для XML-клиента (переход в disconnected и необходимость нового
   `connect`) — **I**; не проверено на захвате (RE-2, эксперимент E05 из плана).

### `FUN_1803d27b0` — переподключение TCP (вызывается только из цикла, `0x180356355`, `0x180356b32`)

- Логирует `"ReConnecting to "` (VA `0x1808482a8`, ссылка `0x1803d29ff`) + адрес сервера из
  `conn+0x810` (два слота по 0x20 байт) + `":"` + порт из `conn+0x850` (индекс слота —
  `conn+0x870`) — **D**.
- Перед попыткой обнуляет «новый SID»: `*(conn->p18 + 1) = 0xff` — **D**.
- `connect()` с таймаутом `min(остаток окна, 10000)` мс (`FUN_1801c2200`); при
  `WSAE... == 10093` делает `WSAStartup` и повторяет с 10000 мс — **D**. После успеха логирует
  `"ReConnected."` и вызывает построитель `FUN_1803d31c0` (`0x1803d3142`); после неудачи
  логирует `"Connect error #<code>, WSAE:<err>"` и возвращает -10 — **D**.

### `FUN_1803d31c0` — построитель RQ_RELOGIN и RQ_RECOVER

1. Сохраняет текущие (сессионные) ключи и подставляет ключ по умолчанию: `0x1803d3242`,
   `0x1803d3261` (слот 0), `0x1803d3282`, `0x1803d32a1` (слот 1); ключ/синхропосылка по
   умолчанию — VA `0x180856010`/`0x180856058` — **D**.
2. **RQ_RELOGIN.** Payload = `Z12`: строка из `conn+0x7e0` длиной до 12 байт + NUL
   (`0x1803d32bf` = `conn+0x7e0`, `0x1803d32c8` = 0xc, `0x1803d32d5` = writer `FUN_1801be3e0`).
   Отправка `FUN_180355d50(conn, stream, 0x3f, "RQ_RELOGIN")` — `0x1803d3378`–`0x1803d3395`
   (строка `RQ_RELOGIN` VA `0x18084a448`) — **D**. Запрос уходит на ключе по умолчанию, как
   первый RQ_LOGIN — **D**.
   **I:** строка в `conn+0x7e0` — логин: ограничение 12 байт совпадает с `Z12:login` в RQ_LOGIN
   (`maxLogin=12` в `native/session`); прямой записи в `conn+0x7e0` в декомпиляции не найдено
   (конфигурация копируется в объект соединения целиком, поиск `0x7e0` по всем инструкциям дал
   только чтения в этих двух функциях). Тождество «логин» подтверждено захватом — **S** (E05:
   payload RQ_RELOGIN = тот же логин + NUL, что в RQ_LOGIN; в фикстуре он маскирован TESTLOGIN).
3. **Ответ RQ_RELOGIN:** `B:len`, `Bn:token` (`len` байт, буфер 0x100), `B:sid`
   (`0x1803d33bd`, `0x1803d33e7`, `0x1803d3430`) — **D**.
4. Проверка «тот же сервер»: `sid` из ответа пишется в `conn->p18[1]` и сравнивается с
   `conn->p18[0]` (SID из ответа RQ_PWD). Если не совпадает — лог
   `" Not same server:<new> instead of <old>"` (строки VA `0x18084a498`, `0x18084a488`) и
   возврат -0xe (`0x1803d3463`–`0x1803d3578`) — **D**. Если байт SID прочитать не удалось —
   сравнение пропускается, считается «тот же сервер» — **D**. На демо-сервере в RQ_PWD приходит
   `SID# 0`, и в ответе RQ_RELOGIN тоже пришёл `sid=0` — проверка прошла (**S**, E05).
5. **RQ_RECOVER.** Payload = `Bn:token` — те же `len` байт токена, **без** префикса длины
   (`0x1803d35e7`–`0x1803d3601`, writer `FUN_1801be5d0`) + `L:lastSeq` — упакованное int32
   из `conn+0x2c` (`0x1803d3611`–`0x1803d3624`, writer `FUN_1801be7d0`) — **D**. Перед
   отправкой возвращаются сессионные ключи (`0x1803d35c0`, `0x1803d35e1`), поэтому RQ_RECOVER
   шифруется прежним сессионным ключом — **D**. Отправка
   `FUN_180355d50(conn, stream, 0x40, "RQ_RECOVER")` — `0x1803d36b4`–`0x1803d36d1`
   (строка `RQ_RECOVER` VA `0x18084a4e0`) — **D**.
6. **Ответ RQ_RECOVER** не разбирается: в `FUN_180355d50` проверяется только кадр — вид «ответ»
   (`flags & 3 == 2`) и тип `0x40` либо тип последнего обычного запроса (`DAT_1809ede40`),
   иначе `"Incorrect server RECOVER response"` (VA `0x18084ed50`, ссылка `0x180357606`) и
   throw — **D**. Живой захват показал, что сервер отвечает **типом последнего обычного запроса**
   (`RQ_MAIN`, type 5) и непустым payload — это отложенный ответ прерванного запроса; payload
   DLL не использует — **S** (E05; кадра type 0x40 не было). Обмена новым сессионным ключом нет:
   в ветке восстановления отсутствуют разбор ключа/синхропосылки — **D**; **I:** сервер хранит
   сессионный ключ по токену — **S** подтвердил, что прежний сессионный ключ продолжает работать
   после RQ_RECOVER (последующий RQ_MAIN читается им).
7. После успеха оборванный запрос повторяется (`goto LAB_180356120`, `0x180356120`) теми же
   ключами — **D**.

### Откуда берутся sid, uid и lastSeq

- **SID** — один байт из ответа RQ_PWD, хранится в объекте сессии `conn+0x18` по смещению 0
  (разбор RQ_PWD в `FUN_1803895c0`; журнальные строки ` SID# ` VA `0x18084a17c`,
  ` UID# ` VA `0x18084a174`) — **D**. В RQ_RELOGIN/RQ_RECOVER не передаётся, используется только
  для сравнения серверов — **D**.
- **UID** — int32 из ответа RQ_PWD, объект сессии `+4` — **D**. В RQ_RELOGIN/RQ_RECOVER не входит
  — **D**. Сигнатура `session.RecoverPayload(sid byte, uid int32, lastSeq ...)` из плана
  декомпиляцией **не подтверждается** (см. блок «Для Go-реализации»).
- **lastSeq** — счётчик запросов `conn+0x2c` (int32): инкрементируется перед **каждым**
  запросом, кроме типов 63/64 (`0x180355f28`, `0x180355f32` исключают 0x3f/0x40; включая
  RQ_LOGIN и RQ_PWD); печатается в журнал как `send #<n>`/`recv #<n>`
  (`FUN_1803d3c80`, `FUN_1803d3710`) — **D**. Значит в RQ_RECOVER уходит номер последнего
  отправленного запроса, включая тот, чей ответ потерян — **I**. E05: lastSeq = **61** =
  RQ_LOGIN + RQ_PWD + 59 обычных запросов первого соединения (**S**). Где счётчик
  обнуляется/инициализируется, в декомпиляции не найдено — **не проверено**.

### Условие выбора: RQ_RECOVER или новый логин

- В цикле восстановления выбора нет: при обрыве всегда RQ_RELOGIN, и если SID совпал — RQ_RECOVER.
  «Новый логин» — это отдельная команда `connect` (`FUN_1803895c0`), в цикл она не входит — **D**.
- Практическая граница — `session_timeout`: пока он не истёк, DLL пытается восстановить сессию
  (точка сохранения `secid` — восстановление не пересобирает каталог); после истечения окна —
  `"Request timeout."`, и новый `connect` пересобирает каталог — **D**/**I**. E05 длинный обрыв
  (150 с > 120 с): DLL сделала 120 попыток с шагом ~1 с, через ~120.5 с бросила
  `RQ_MAIN [-1] Request timeout.`, отдала `<server_status connected="false"/>` и после возврата
  прокси **не** переподключилась сама — новый логин автоматически не делается (**S**).

| -0x9 | прочие ошибки send/recv (кроме 0x3ed ниже) | **D** (`FUN_1803d3710`, `FUN_1803d3c80`) |
| -0xb | приём: `WSAGetLastError() == 0x3ed`; `FUN_1801bfef0` ставит 0x3ed при несовпадении CRC-16 payload (0x3ec — CRC заголовка, 0x3eb — длина > 0xfff0) | **D** |
| -0xc | запрошен shutdown | **D** |
| -0xd | BYE от сервера (`flags & 3 == 3`) | **D** |
| -0xe | «Not same server»: SID в ответе RQ_RELOGIN не совпал с сохранённым | **D** |
| -0x10 / -0x11 / -0x12 | recv timeout / send timeout / reconnect (имена из `FUN_1803df570`) | **D** |
| -10 | ошибка записи payload/буфера | **D** |

Фатальные исходы цикла (все — C++ throw через `FUN_18073a228`):

- `"Recover unavailable."` (VA `0x18084eb30`, ссылка `0x180356564`): `ret != -0xe` и
  (`p18[0] == 0` или `p18[0] == p18[1]`) и (`ret == -0xd` или (`тип кадра == 0x40` и
  `ret == -0xb`)) — **D** (ассемблер `0x1803564e1`–`0x1803565b9`, второй экземпляр
  `0x180356cbe`–`0x180356d9c`).
- `"Recover limit exceeded."` (VA `0x18084ea88`, ссылка `0x180356481`): в этой сборке ветка
  **недостижима** — флаг `[RSP+0x40]` обнуляется в начале каждой итерации (`0x1803563a5`) и
  больше нигде не записывается (во втором экземпляре цикла — `[RSP+0x42]`, `0x180356b82`) — **D**.
  Таймер «2×session_timeout», выставляемый для этого сценария (`0x18035639a`), тоже нигде не
  читается — **D**. Счётчик подряд идущих -0xe (`[RSP+0x34]`, `0x180356370`) увеличивается, но не
  сравнивается ни с каким лимитом — **D**. Итог: фактического лимита повторов в DLL 6.47 нет,
  ограничивает только окно `session_timeout`.
- `"Request timeout."` — окно истекло (`0x1803565cb`–`0x1803565f6`, `0x18035720f`) — **D**.
- `"Incorrect server RECOVER response"` — неверный кадр ответа RQ_RECOVER (`0x180357606`) — **D**.
- Практическое чтение условий (сверено с реализацией): `-0xe` («Not same server») **не** фатальна —
  попытки повторяются до окна; `-0xd` (BYE) фатальна; ошибка CRC payload (`-0xb`) фатальна
  только когда повреждён кадр типа `0x40` (ответ RQ_RECOVER); неверный ответ RELOGIN/RECOVER —
  немедленный throw.

### `recover="true"` в XML

- DLL выводит атрибут ` recover="true"` в `<server_status>` (`FUN_1800ffcf0`, ссылка
  `0x1800fff7b`, строка VA `0x18082e980`), сразу после `connected="…"`; условие — сигнальное
  состояние события `param_1+0x2b0` (`WaitForSingleObject(...) == 0`) — **D**. E05: атрибут
  приходит **сразу при потере связи** (в момент первой строки `ReConnecting to …`), а после
  успешного восстановления — обычный `connected="true"` без `recover` (**S**).
- Входного атрибута `connect` с именем `recover` в бинаре не найдено: строки `"recover"` нет
  (есть только ` recover="true"` для вывода) — **I**; отсутствие могло быть скрыто сравнением имён
  по хешу, проверить (RE-2). Параметры `session_timeout`/`request_timeout` в `<connect>` есть
  (строки VA `0x18082de88`, `0x18082dec0`, парсер `FUN_1801196a0`) — **D**.

### Подтверждение живым захватом (RE-2, E05) — S

2026-11-04, демо-сервер Finam, DLL 6.47.2.26.4 под Wine 11.21, логирующий прокси
(`tools/tcproxy`), прогон `tools/re/reference-harness`. Два сценария: короткий обрыв (прокси
убит на ~5 с) и длинный (150 с > `session_timeout`). Сырые захваты и логи — вне git
(`.re-run/cap/`, `.re-run/e05/`); обезличенные фикстуры —
`native/session/testdata/recover-{short,long}-live.{hex,xml,md}`.

- **RQ_RELOGIN payload = `Z12: login`**, и это тот же логин, что в RQ_LOGIN: в захвате
  `TESTLOGIN`+NUL (после обезличивания), совпадение с полем логина RQ_LOGIN побайтное — **S**.
- **RQ_RELOGIN reply = `B:len, Bn:token, B:sid`**: len=135, token 135 байт, `sid=0`, лишних
  байт нет — **S**. `sid=0` совпал с SID из RQ_PWD (`SID# 0`), проверка «тот же сервер» прошла.
- **RQ_RECOVER payload = token (135 байт, без префикса длины) + `L:lastSeq`**: lastSeq = **61**
  (байты `d1 03`) = RQ_LOGIN + RQ_PWD + 59 обычных запросов первого соединения — **S**.
- Ключи: RQ_RELOGIN принят на ключе по умолчанию, RQ_RECOVER — на прежнем сессионном; после
  восстановления тот же сессионный ключ работает для RQ_MAIN — **S** (обмена ключами нет).
- **Ответ RQ_RECOVER** — кадр `type=5` (RQ_MAIN, тип прерванного запроса), payload 2216 байт
  (отложенный ответ); кадра `type=0x40` не было, DLL приняла восстановление — **S**. Это
  уточняет RE-1: reply-кадр может нести отложенный ответ исходного запроса.
- После восстановления DLL **не** шлёт RQ_LOGIN/RQ_PWD/RQ_STARTUP и не переэмитит справочники/
  бумаги: 40 с второго соединения — только RQ_MAIN (+ RQ_LOGOUT на disconnect) — **S**.
- Тайминг короткого сценария (`*_ts.log`): обрыв 21:38:09.352 (`ReConnecting to 127.0.0.1:39100...`),
  при недоступном прокси `Connect error #8: … WSAE:10061` каждые ~1.004 с, `ReConnected.`
  21:38:15.379, ` Recover succeeded.` 21:38:15.676 — **S** (фиксированный шаг 1 с, рукопожатие ~0.3 с).
- `session_timeout`: сервер прислал 120, DLL залогировала `Session timeout 120000 ms.` и
  `Request timeout 20000 ms.` — **S** (единицы: секунды с сервера → мс внутри).
- Длинный обрыв: 120 попыток `ReConnecting to …` с 21:42:32.510 по 21:44:32.050, затем
  `RQ_MAIN [-1] Request timeout.` в 21:44:33.055 и колбэк `<server_status … connected="false"/>`;
  после возврата прокси (21:45:02) DLL не переподключилась, команды отвечают
  `<result success="false"><message>Cannot process this command without connection.</message></result>`
  (`disconnect` — «Соединение не установлено…») — **S**.
- `recover="true"`: приходит **в момент потери связи**, атрибуты в порядке
  `sys_ver, build, server_tz, id, connected, recover`; после успеха — `connected="true"` без
  `recover`; `connected="false"` — на disconnect/по таймауту — **S**.
- `"Recover unavailable."` / `"Recover limit exceeded."` в живых прогонах не появились — **S**
  согласуется с **D**-находкой о недостижимой ветке limit.

### Для Go-реализации

Точный layout payload (порядок байт на проводе; примитивы — из таблицы «Типы полей»):

```
RQ_RELOGIN (63):  Z12: login                 // логин до 12 байт + NUL; шифруется ключом по умолчанию
RQ_RECOVER (64):  Bn:  token                 // ровно len байт токена из ответа RQ_RELOGIN, без длины
                  L:   lastSeq               // int32, упакованное целое
```

- Ответ RQ_RELOGIN: `B:len`, `Bn:token` (`len` ≤ 255, буфер 256), `B:sid`. Ответ RQ_RECOVER:
  кадр — вид «ответ», тип `0x40` **или тип последнего обычного запроса**; payload может нести
  отложенный ответ прерванного запроса (E05: type 5, 2216 байт) и не используется — **S**.
- Ключи: RQ_RELOGIN — `wire.DefaultKeys()` (ключ/синхропосылка по умолчанию), RQ_RECOVER —
  сохранённые сессионные ключи; после восстановления сессионный ключ не меняется.
- Предлагаемые сигнатуры (план `session.RecoverPayload(sid byte, uid int32, lastSeq ...)` по RE-1
  неверен: sid/uid в payload не входят):

  ```go
  // ReloginPayload builds RQ_RELOGIN: Z12: login.
  func ReloginPayload(login string) []byte

  // RecoverPayload builds RQ_RECOVER: Bn: token from the RQ_RELOGIN reply, then L: lastSeq.
  func RecoverPayload(token []byte, lastSeq int32) []byte
  ```

- Состояние, которое нужно хранить в `Client`: `login`; `sid` из RQ_PWD (для сравнения);
  `seq int32` — счётчик запросов, +1 на каждый запрос кроме 63/64 (реализован в
  `session.Conn.seq`, доступен через `LastSeq()`); сессионные ключи (они нужны на новом сокете).
- Алгоритм восстановления, как у DLL: новый TCP → `RQ_RELOGIN` ключом по умолчанию (таймаут
  `min(остаток окна, 10 с)`) → прочитать `token`/`sid`, строго сравнить SID (расхождение, в том
  числе при сохранённом SID=0, — `ErrNotSameServer`/DLL -0xe) → `RQ_RECOVER` сессионным ключом с
  `lastSeq` → повторить оборванный запрос. Первая попытка сразу, далее ровно раз в 1 с, окно —
  `session_timeout`; после окна DLL бросает `"Request timeout."` и сама новый логин не делает.
- Живым захватом (RE-2, E05) **подтверждены** байты обоих запросов и ответа RQ_RELOGIN
  (см. «Подтверждение живым захватом» ниже). Осталось не проверенным: ветка «сервер забыл
  сессию» (BYE/-0xd или «Recover unavailable.»), счётчик в «`Not same server`» (-0xe) на живом
  обмене, начальное значение/сброс lastSeq и входной атрибут `recover` у `<connect>`.

**Состояние Go-реализации (2026-11-04).** `native/session` содержит `ReloginPayload`,
`RecoverPayload`, `ParseReloginReply` и `Conn.Restore` (строгий SID, сохранённые ключи, счётчик
`lastSeq`); `native/recover.go` повторяет DLL: первая попытка сразу, далее раз в 1 с, окно
`session_timeout`; BYE и неверный ответ RELOGIN/RECOVER фатальны сразу, CRC payload фатальна
только для кадра 0x40, а `-0xe` (чужой SID) повторяется до окна. Как и DLL, клиент
**не** делает автоматический новый логин после окна: `Client.Run` возвращает экспортированный
`*native.RecoveryError` (проверка `errors.As`; `errors.Is(err, native.ErrRecoveryTimeout)` —
окно истекло, `errors.Is` также видит последнюю ошибку попытки, например `session.ErrBye`), а
явный `Client.Reconnect(ctx)` выполняет полный connect (новый TCP, логин, `load`, пересборка
каталога и переподписка по `model.Symbol`) — это Go-обёртка над XML-командой `connect`.
Порядок статусов в потоке `Run` повторяет E05: `ServerStatus{Recover:true}` сразу на обрыве,
затем plain `ServerStatus{Connected:true}` после успеха либо `ServerStatus{Connected:false, Err}`
при сдаче; `Connector` рендерит их как `<server_status ... connected="true" recover="true"/>`,
`<server_status ... connected="true"/>` и `<server_status ... connected="false"/>`.

## Параметры `<connect>` (PDF 3.1): куда уходит каждый

Разбор обработчика команды `connect`: `FUN_1801196a0` (XML-элемент `<command id="connect">`,
параметры — дочерние элементы; `FUN_18040c140(el, "имя")` возвращает элемент, `FUN_18040d930` —
его текст, `FUN_18012f330` проверяет число, `FUN_180781710` переводит в int). Статусы: **D** —
декомпилятор, **S** — подтверждено живым захватом (RE-2, два логина DLL через прокси, 2026-11-04,
фикстуры и сырьё — `.re-run/r6/`).

### Живая сверка (S): два логина DLL через прокси

Прогон A — `<connect>` только с логином/паролем/host/port/rqdelay=100 (все параметры по умолчанию);
прогон B — те же плюс `<autopos>true</autopos><micex_registers>true</micex_registers>
<utc_time>true</utc_time><push_u_limits>10</push_u_limits><push_pos_equity>10</push_pos_equity>`.
Демо-сервер, одна машина, ~42 с после загрузки. Результаты:

- **Не изменилось ничего в протоколе** от `autopos/utc_time/milliseconds/push_*`: RQ_LOGIN payload
  (18 байт) побайтно равен, RQ_STARTUP reply (4355 байт) побайтно равен, хвост RQ_PWD после proof
  (строки host/user/OS, HWID, адреса, trailer) побайтно равен; набор кадров одинаков:
  1×RQ_LOGIN, 1×RQ_PWD, 3×RQ_TIME, 1×RQ_STARTUP, 1×RQ_CLIENT_HOLDINGS, поток RQ_MAIN, 1×RQ_LOGOUT — **S**.
  Отличалась только длина RQ_PWD (196 vs 204) из-за длины challenge от сервера (ответ RQ_LOGIN
  130 vs 138 байт, challenge 128 vs 136) — серверный параметр, не клиентский.
- `micex_registers=true` → в `<positions>` появляется `<register>T0</register>` внутри
  `<money_position>` (в default тега нет); остальные колбэки идентичны (766/766) — **S**.
- `push_u_limits=10`/`push_pos_equity=10` за ~42 с **не дали** ни одного нового кадра
  (типы 43/16/17/81 не появились) — **S**-негатив; почему в этом прогоне таймеры не сработали, не
  установлено (D: регистрация таймера есть, см. таблицу). Нужен отдельный прогон/RE-3.
- `utc_time`/`milliseconds` в этом сценарии ненаблюдаемы: колбэков со временем нет (нет подписок);
  по **D** они влияют только на форматирование XML — оставлено «не проверено».
- `language=en` отдельным прогоном: последний байт RQ_PWD = **1** (у default 0), а словари в
  колбэках приходят на английском (`MICEX`, `Auction`, `1 minute` вместо `ММВБ`, `Аукцион`,
  `1 минута`) — **S**: `language` действительно уходит в RQ_PWD и влияет на серверные справочники.
- `rqdelay` подтверждён логом `"Main thread OK. Data refresh period: 100"` и шагом RQ_MAIN ~100 мс — **S**.

  `push_*` — секунды, минимум 1.
- Фикстура ожидаемого вывода трёх служебных команд — `native/testdata/service-dll.xml`
  (см. [commands.md](commands.md)).

## После логина

- **RQ_TIME** (`FUN_1803b7ca0`): пустой запрос; ответ `L:время` + 16 байт часового пояса. Время — секунды «настенного» времени сервера (МСК на демо), DLL печатает его как `Server time`. Первые 2 байта пояса на демо: `-180` (int16 LE, минуты) — **I**. Демо-сервер присылает этот ответ с флагом `0x82` (без шифрования) — **S**.
- **RQ_STARTUP** (`FUN_180355ce0`): пустой запрос; ответ — справочники (рынки, режимы, CP1251), 4355 байт на демо. Формат пока не разобран.
- **RQ_MAIN** (`FUN_18038d7d0`): пустой запрос; ответ — поток записей `B:tag …`, около сотни типов. Тег `0x5f` (`R_WRAPPER`) — запись с длиной, её можно пропустить. Если `65520 − len(ответ) < 500`, DLL сразу повторяет RQ_MAIN, иначе ждёт `rqdelay`. На демо и DLL, и Go получают первый неполный ответ на 35-м опросе (≈2.26 МБ) — это критерий выборки снапшота — **S**. Признак DLL «Snapshot done» зависит от разбора записей (M5).
- **RQ_LOGOUT** (`FUN_18038d720`): пустой запрос, DLL не ждёт ответа (таймаут 4000 мс, приём не выполняется); сервер ответа не присылает — **S**.
- Часть ответов RQ_MAIN приходит с флагом `0x82` (payload без шифрования); CRC проверяется всегда.
- Сжатия на демо не наблюдалось: payload — открытые записи.

## Что не доказано

- Смысл большинства полей ответа RQ_PWD, флагов 4/8 RQ_LOGIN и слов `W:1`, `W:540`.
- Форматы RQ_STARTUP и записей RQ_MAIN; признак «Snapshot done»; RQ_CLIENT_HOLDINGS; сжатие (`inflate 1.2.5`, на демо не встречалось) — этап M5.
- RQ_RELOGIN/RQ_RECOVER: байты payload, формат ответа RQ_RELOGIN (включая SID=0), lastSeq и «логин в Z12» подтверждены живым захватом (RE-2, E05, раздел «Переподключение и восстановление» выше); не подтверждена только ветка «сервер забыл сессию» (BYE/-0xd, «Recover unavailable.»).
- Параметры `<connect>`: живой эффект `push_u_limits`/`push_pos_equity` (в прогоне 10 с новых запросов не дали — S-негатив) и форматирование XML от `utc_time`/`milliseconds` (нужны колбэки со временем) не проверены; связь `packet_size` с `W:65512` в RQ_LOGIN — **I**.
- Поведение на боевом сервере и на HFT-адресах; демо-сервер может отличаться.
- Режимы с внешней криптографией (MS CryptoAPI, MESPRO, SSL; `cfg+8 != 0`) не реализованы.

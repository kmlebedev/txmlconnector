# TRANSAQ: серверная сторона и подсказки для портирования

Дата исследования: 11 сентября 2026. Метод: первичные публичные источники, чтение локального Go-кода, статический разбор PE и ASCII-строк. DLL не исполнялась; к серверам не подключались. Дизассемблирование графа функций и динамическая проверка пока не выполнены.

## Основной вывод

Найдены конкретные точки входа для восстановления протокола: группы `RQ_*`, сообщения handshake, классы криптографии и сокетного потока, следы распаковщика. Материала достаточно, чтобы начать адресный анализ, но недостаточно для описания формата пакетов или рабочего Go-клиента.

В просмотренных первичных источниках не найдена полная спецификация сетевого обмена DLL ↔ сервер. Публичное описание XML API не доказывает, что сетевой формат тоже XML. Наличие собственных типов запросов в бинарнике усиливает гипотезу отдельного внутреннего протокола; формат подтвердит трассировка.

## Что опубликовано о сервере

TRANSAQ описывает сервер как центральный компонент брокерской системы, связанный с биржами через шлюзы. Отдельно представлены Connector, FIX и COM-интерфейс TACCESSOR; есть учебный продукт Intra и модуль параллельных серверов. Эти сведения описывают продуктовые возможности, а не конфигурацию конкретного брокера. [Официальный сайт TRANSAQ](https://www.transaq.ru/).

Практические выводы исследования:

- Реализация клиента не требует воссоздавать биржевые шлюзы или серверную базу данных.
- FIX имеет смысл уточнить у брокера как альтернативный маршрут доступа. Его наличие в линейке не означает доступность на Connector-порту или эквивалентность набора данных.
- Intra — кандидат для лаборатории. Совместимость его доступа с данной DLL и нужными сценариями ещё нужно подтвердить.
- Переход на резервный адрес должен быть отдельным экспериментом: перенос состояния сессии между серверами пока не доказан.
- Опубликованные требования к серверной ОС содержат старые версии Windows; из них нельзя определить текущее устройство серверов Финама.

На странице Финама опубликованы адреса обычного Connector: `tr1.finam.ru:3900`, резерв `tr2.finam.online:3900`; HFT: `hft.finam.ru:13900`, резерв `hft1.finam.ru:13900`. Для обычного и HFT-варианта указаны отдельные дистрибутивы версии 2.26.4 от 09.09.2025. Доступ оформляется как сервис брокера. Адреса проверены по странице, доступность сети не проверялась. [Финам: TRANSAQ Connector](https://www.finam.ru/howtotrade/soft/tconnector/).

Вывод: endpoint, профиль доступа и вариант DLL фиксировать вместе; совместимость обычного и HFT-протокола не предполагать. Общая дата/версия дистрибутива не доказывает идентичность бинарников.

### Первые адреса для Ghidra

| Ориентир | RVA |
|---|---|
| Экспорт `SendCommand` | `0x179ec0` |
| Экспорт `Initialize` | `0x17a500` |
| Экспорт `GetServiceInfo` | `0x17b1a0` |
| Строка `RQ_LOGIN` | `0x849428` |
| Строки `RQ_HANDSHAKE` | `0x849708`, `0x8498d8` |
| Строка `HANDSHAKE: Cryptokey` | `0x849808` |
| Строка `HANDSHAKE: Cryptosync` | `0x849820` |
| Строка версии inflate | `0x85c870` |
| RTTI `CSocketStream` | `0x9c9928` |
| RTTI `AesCtrCipher` | `0x9c9f80` |

Адреса строк не являются адресами функций. Для runtime: VA = фактическая база загрузки + RVA; учитывать ASLR. Инвентарь содержит также файловые смещения, которые нельзя подставлять вместо RVA. Предпочтительная PE-база — `0x180000000`.

Наличие `initSvr` внутри клиентской DLL может означать общий библиотечный код; оно не доказывает, что DLL содержит полноценный сервер. Аналогично, названия логов не позволяют восстановить порядок вызовов по соседству строк в файле.

## Эксперименты, которые дадут максимум информации

Это предложенные исследования, а не результаты уже проведённых сетевых проверок.

| ID | Эксперимент | Какие доказательства собрать |
|---|---|---|
| E01 | Два свежих успешных подключения с одинаковыми настройками. | Различающиеся сессионные значения, сообщения до/после login, реальный критерий ready. |
| E02 | В отладчике пройти от ссылок на handshake к чтению/записи сокета. | Числовые типы запросов, границы буферов, длины, стеки вызовов и порядок преобразований. |
| E03 | Установить реально созданный объект криптографии и трассировать его методы. | Выбор vtable, формат ключевого материала, IV/счётчик, состояние между сообщениями; независимые тестовые векторы. |
| E04 | Отследить вызовы распаковщика на большом ответе справочников/истории. | Связь с сетью, формат потока, границы reset и ограничение выходного размера. |
| E05 | Краткий обрыв, затем обрыв длиннее настроенного окна; отдельно новый процесс. | Отличия relogin/recover от холодного входа, сохранённые идентификаторы, повторы и пропуски событий. |
| E06 | В последовательных сессиях менять только `rqdelay`, например 10/100/1000. | Какие исходящие поля меняются, частота и состав входных обновлений; не смешивать это с задержкой callback. |
| E07 | Подписка на один инструмент, затем на второй; отписка от первого. | Маппинг подписок, обновления против снимков, поведение после reconnect. |
| E08 | История для одного инструмента с изменением одного параметра. | Поля запроса, порядок/пакетирование ответа и признак завершения. |
| E09 | Разделить TCP-данные и объединить соседние записи на локальном стенде/replay. | Парсер не зависит от границ send/recv; корректно обрабатывает незавершённые сообщения. |
| E10 | На тестовом счёте оборвать связь после отправки заявки до получения ответа. | Механизм выяснения исхода и доступность корреляции с операцией сервера. |

Один pcap не раскрывает внутренние буферы, а один дамп памяти не раскрывает семантику сессии. Для ключевых сценариев нужны одновременно XML-журнал, сетевой поток и трасса функций. После обнаружения нескольких соединений фиксировать роль каждого, не объединять их в предполагаемый единый канал.

## Что уточнить у брокера/разработчика

Подготовленные вопросы, сообщения не отправлялись:

1. Есть ли тестовый Connector endpoint, пригодный для воспроизводимых сессий и тестовых заявок; какой криптопрофиль он требует?
2. Доступна ли спецификация wire-протокола, SDK для другой ОС/архитектуры либо интерфейс по договору/NDA?
3. Есть ли разрешённый FIX-доступ с нужными рыночными данными и историей; каковы отличия функциональности?
4. Каковы правила нескольких сессий одного пользователя, восстановления на резервном сервере, ограничения запросов и поддерживаемые версии клиента?
5. Можно ли получить matching PDB или диагностическую сборку исследуемой версии, и чем обычный/HFT-дистрибутивы отличаются на уровне обмена?

## Воспроизведение локального анализа

Из корня репозитория `txmlconnector`:

```sh
python3 docs/research/inspect_binary.py txmlconnector64-6.47.2.26.4.dll docs/research/binary-inventory-6.47.2.26.4.json
objdump -p txmlconnector64-6.47.2.26.4.dll
```

Скрипт использует только стандартную библиотеку Python, читает файл как данные и не загружает DLL. Он предназначен для данного PE32+ образца, не является универсальным валидатором недоверенных PE. Найдено 9 именованных экспортов и 730 отобранных ASCII-ориентиров, включая повторы. UTF-16-строки и полный RTTI-граф ещё не исследованы.

Для следующего этапа: [Ghidra](https://github.com/NationalSecurityAgency/ghidra) для ссылок, типов и декомпиляции; [x64dbg](https://help.x64dbg.com/en/latest/) для подтверждения исполняемого пути на Windows. Установку и запуск этих средств в рамках данного анализа не выполняли.

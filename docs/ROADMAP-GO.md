# Roadmap: нативный TRANSAQ Connector на Go

Дата: 11 сентября 2026. Статус: план; предварительный статический анализ выполнен, сетевой протокол ещё не восстановлен.

## Цель и границы

Создать реализацию на Go, которая напрямую взаимодействует с сервером TRANSAQ и выполняется на Linux/macOS, amd64/arm64 без Windows DLL, Wine и эмуляции x86. Для основного поддерживаемого профиля целевая сборка — `CGO_ENABLED=0`.

Результат исследования — проверяемая спецификация и новый исходный код. Декомпиляция даёт материал для восстановления поведения, но не возвращает исходный проект автора. Совместимость с C ABI DLL не входит в MVP; сохраняем прикладной Go/XML-контракт. Зависимость от серверного API и доступа брокера остаётся.

Начальная область: один согласованный сервер, один криптографический профиль, рыночные данные и история для существующего экспортёра. Торговые операции — отдельный этап после стабилизации чтения. HFT, дополнительные криптопровайдеры, новости, РЕПО и сложные поручения включаются по матрице покрытия.

Исследование серверной стороны и конкретные бинарные ориентиры находятся в [TRANSAQ-SERVER-RESEARCH.md](TRANSAQ-SERVER-RESEARCH.md).

## Этапы и критерии завершения

| Этап | Работа | Артефакт и критерий выхода | Зависимость |
|---|---|---|---|
| M0. База | Зафиксировать бинарник, документацию, настройки и профиль тестового доступа. Согласовать список команд и условия публикации. | Паспорт, список платформ, матрица покрытия, доступный эталонный стенд. | Нет |
| M1. Эталон | Go-harness на Windows x64: команды, ответы, callbacks, монотонное время, идентификатор запуска, сетевой захват. | Повторяемые сценарии connect, disconnect, справочники, подписка, история и отказ. | M0 |
| M2. Карта DLL | Ghidra: экспорты, XML-dispatch, сетевые классы, криптография, чтение сообщений. Выделить runtime и сторонние библиотеки. | Аннотированные функции/RVA и пути XML → сеть → XML для выбранных сценариев. | Паспорт M0 |
| M3. Протокол сессии | Сопоставить захват с отладчиком: framing, handshake, login, версия, преобразования, reconnect. | Спецификация с полями, направлениями, примерами, неизвестными и тестовыми векторами. | M1 + M2 |
| M4. Прямое подключение | Минимальный Go-клиент для одного криптопрофиля. | Новая сессия, штатная аутентификация, разбор начальных данных, готовность и logout без DLL. Повторить в независимых запусках. | M3 |
| M5. Рыночный MVP | Справочники, котировки/сделки/стакан, subscribe/unsubscribe, свечная история, восстановление. | Экспортёр работает через Go-backend; покрытые сценарии проходят сравнение с эталоном. | M4 |
| M6. Торговля | Постановка, отмена, изменение, исполнения, позиции и сверка после разрыва. | На отдельном тестовом счёте проверены подтверждённые и неопределённые исходы. | M5 |
| M7. Переносимость | Выполнение на целевых ОС/CPU, нагрузка, длительная сессия, совместимость версий. | Отчёт с измерениями, известными ограничениями и процедурой переключения backend. | M5; M6 для торгового релиза |

M1 и M2 можно вести независимо после фиксации бинарника. Главный рубеж — M4: до него не обещаем срок полной реализации. Если препятствие связано с неподдержанным криптопровайдером, недоступным тестовым доступом или серверным требованием, фиксируем точную причину и пересматриваем профиль поддержки.

## Первый исследовательский цикл

Предлагаемый бюджет — 10 рабочих дней одного инженера, как ограничение исследования, а не обещание готовности протокола.

1. Дни 1–2: завершить паспорт, подготовить Windows-стенд и harness, записать успешный эталонный connect.
2. Дни 3–4: найти ссылки на `RQ_HANDSHAKE`, `RQ_LOGIN`, `RQ_STARTUP`, `RQ_MAIN`; восстановить ближайшие функции и типы.
3. Дни 5–7: сопоставить внутренние буферы и сетевой поток, установить выбранный криптопрофиль, восстановить минимальный обмен.
4. Дни 8–10: попытка независимого подключения из Go; повторный запуск с новыми сессионными значениями; отчёт о доказанном и неизвестном.

Выход цикла: воспроизводимый корпус, карта функций, черновик спецификации и работающий M4 либо конкретный блокер с планом следующего эксперимента. При отсутствии Windows/учётной записи выполняется статическая часть; это не считается подтверждением M4.

## Архитектура реализации

```text
Go-клиент / gRPC / экспортёр
             |
     connector.Connector
             |
       XML compatibility
             |
  session + command handlers
             |
  wire codec + crypto profile
             |
        TCP transport
             |
      TRANSAQ server
```

Предлагаемые новые пакеты: `internal/wire`, `internal/session`, `internal/cryptoprofile`, `internal/xmlcompat`; конкретное размещение уточнить на M4. Существующие `client`, `proto` и `server` использовать как потребителей совместимого backend.

Принципы:

- Один владелец состояния сессии; явные переходы connecting/authenticating/loading/ready/recovering/closed. Это проектная модель, ещё не реконструкция внутренних состояний DLL.
- Framing отделён от шифрования и сжатия; порядок преобразований устанавливается экспериментом.
- Цены и количества хранятся без потери точности; формат wire-чисел восстанавливается отдельно от XML-представления.
- Очереди ограничены; переполнение и потеря целостности потока обнаруживаются и сообщаются.
- Переподключением к TRANSAQ управляет один слой. Текущий клиентский reconnect необходимо согласовать с новым backend, чтобы избежать конкурирующих циклов восстановления.
- Неподдерживаемая команда возвращает явную ошибку. Базовый профиль не подменяет неизвестную криптографию приблизительной реализацией.

## Спецификация и доказательства

Для каждого сообщения сохранять: направление, условие отправки, framing, идентификатор типа, поля/размеры/порядок байтов, преобразования, соответствующие XML-события, влияние на состояние, обработку ошибок. Числовые opcodes не выводить из названий диагностических строк.

Каждое утверждение связывать с SHA-256 DLL, RVA функции или строки, идентификатором эксперимента и ссылкой на документацию. Размечать статус: наблюдение, гипотеза, подтверждено несколькими запусками. Псевдокод декомпилятора проверять по дизассемблеру и runtime, особенно размеры типов и указатели.

Структура исследовательских материалов:

```text
docs/ROADMAP-GO.md
docs/TRANSAQ-SERVER-RESEARCH.md
docs/research/inspect_binary.py
docs/research/binary-inventory-6.47.2.26.4.json
docs/protocol/                 # создать на M3
testdata/protocol/             # обезличенные fixtures на M3
tools/reference-harness/       # создать на M1
```

Сырые захваты с логинами, ключами и данными счёта хранить отдельно от публикуемого корпуса. Для fixtures использовать тестовые/синтетические значения, сохраняя согласованность длин и контрольных полей.

## Проверки

| Область | Проверка |
|---|---|
| Framing | Разбиение на каждой границе, объединение сообщений, EOF в середине, неверные длины, ограничение размера распаковки. |
| Кодеки | Эталонные векторы; независимый encoder/decoder oracle, а не только round-trip собственной реализации. |
| Сессия | Холодный вход, краткий обрыв, длительный обрыв, смена endpoint, отключение в каждой фазе. |
| Данные | Один входной replay для сравнения с DLL; живые потоки сравнивать с учётом различий времени и подписок. |
| Торговля | Потеря ответа после отправки, повторный callback, частичное исполнение, сверка активных заявок. Не повторять неизвестный исход автоматически. |
| Время и деньги | Граница суток, переходы временных зон, точность цены, пустые и нулевые значения. |
| Эксплуатация | `go test`, race detector на поддерживаемых платформах, fuzzing парсеров, нагрузка на ожидаемом пике. |
| Платформы | Реальное выполнение linux/amd64, linux/arm64, darwin/amd64, darwin/arm64; кросс-компиляция одна недостаточна. |

Для M7 предлагается минимум одна полная торговая сессия и отдельный прогон с восстановлением связи. Порог CPU/RAM/latency установить по измерениям эталона на M1; заранее обещать HFT-производительность нельзя.

## Управление рисками и выпуск

- Неизвестный handshake: ограничить первый цикл M4 и измерять прогресс по восстановленным полям и независимым векторам.
- Профиль криптографии требует платформенного провайдера: явно ограничить поддержку или выделить отдельный backend; portable pure Go не считать автоматически достижимым для всех режимов.
- Обновление сервера: хранить профиль совместимости и записи версии; неизвестный формат диагностировать, а не молча игнорировать.
- Расхождение локальных вычислений DLL и серверных данных: для каждой функции определить место вычисления через трассировку.
- Переключение backend: первоначально сравнивать чтение; торговые команды направлять только одному исполнителю. Эталонный backend сохранять для диагностики и возврата.

Релиз считается нативным только если покрытые операции выполняются прямым Go-клиентом без вспомогательного процесса, загружающего DLL. Полнота совместимости определяется опубликованной матрицей, а не одним успешным login.
